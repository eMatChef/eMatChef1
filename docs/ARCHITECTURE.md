Stand: Code im Repository. Betriebliche Details: [CONTRIBUTING.md](../CONTRIBUTING.md), [APP-ON-DROPLET.md](./APP-ON-DROPLET.md), [deploy/SERVER-UPDATE.md](../deploy/SERVER-UPDATE.md).

## Laufzeit

| Teil | Technik | Ort |
| --- | --- | --- |
| SPA | Vue 3, Vite, Vue Router, Pinia, Vuetify, vue-i18n, Axios | `frontend/` |
| API | Symfony 6.4, PHP ≥ 8.1, Doctrine ORM | `backend/` |
| DB | PostgreSQL 16 | Service `db` in `docker-compose.yml` |
| Lokal | Docker Compose: `db`, `backend` (:8081), `frontend` (:5173), `nginx` (:80), Adminer (:8082) | Repo-Root |
| Öffentliche Dokumentation | VitePress | separates Repository [eMatChef/documentation](https://github.com/eMatChef/documentation) (`docs.ematchef.ch`) |

Die HTTP-API sind Symfony-Controller mit `#[Route('/api/…')]` (`backend/config/routes.yaml`). `api-platform/core` ist installiert und unter `/api` geroutet; Entities haben keine `ApiResource`-Attribute. Neue Endpunkte als Controller anlegen, nicht als zweite API-Platform-Schicht.

## Frontend

### URL-Struktur

| Bereich | URL |
|---|---|
| Global | `/login`, `/register`, `/forgot-password`, `/reset-password`, `/profile/*` |
| Department-Einstieg | `/{departmentId}` — wählt je nach Department-Typ die kanonische Start-URL |
| Grossanlass | `/{departmentId}/ga/…` (Start: `/ga/dashboard`) |
| Normales Department | `/{departmentId}/dept/…` (Start: `/dept/dashboard`) |

Es gibt keine Legacy-Redirects für frühere Pfade ohne `ga/` bzw. `dept/`. Interne und vom Backend erzeugte Links (Benachrichtigungen, E-Mails, Media-Verwendungslinks) zeigen direkt auf die kanonischen URLs. Bewusste Kompatibilitätsentscheidung: bereits versandte E-Mails und gespeicherte Benachrichtigungen mit alten Pfaden führen auf eine unbekannte Seite. API-Pfade (`/api/…`) sind unverändert.

| Bereich | Pfad |
| --- | --- |
| Routen | `frontend/src/router/index.ts` |
| Seiten | `frontend/src/views/` |
| UI | `frontend/src/components/` |
| HTTP | `frontend/src/api/` (ein Modul pro Ressource, `apiClient.ts`) |
| Zustand | `frontend/src/stores/` (Auth, Permissions, …) |
| Texte | `frontend/src/locales/*.json`, Einstieg `frontend/src/i18n.ts` |

**Globales Profil** (`/profile`, kein Department und keine Department-Rolle nötig; nur Anmeldung): eine Seite `ProfileLayout` mit Tabs und eigener URL je Bereich, benannte Routen vor `/:departmentId` (Meta `globalProfile`, der Router-Guard leitet sie nie auf Department- oder Pending-Seiten um).

| URL | Route | Inhalt |
| --- | --- | --- |
| `/profile` | `Profile` | Persönliche Angaben, Sprache, Farben, Adresse, Passwort, Führerausweis (`ProfileBasicsView`, State und Speichern in `useProfileForm`) |
| `/profile/security` | `ProfileSecurity` | TOTP/Recovery-Codes, Sitzungen und Trusted Devices, Sicherheitsaktivität |
| `/profile/emails` | `ProfileEmails` | Hauptadresse, zusätzliche Adressen, Benachrichtigungsadresse je Department (`ProfileEmailsSection`) |
| `/profile/identities` | `ProfileIdentities` | Verknüpfte Anmeldungen (Google, MiData); wertet den OAuth-Rückweg aus |
| `/profile/departments` | `ProfileDepartments` | Department-Mitgliedschaften (nur lesend) und weitere MiData-Zugehörigkeiten |

- Die Bereiche verwenden die bestehenden `ProfileSecurity*`-Sektionen und `/api/profiles/{id}/…`; es gibt keine eigenen Profil-Endpunkte für die Seiten. Aufrufe laufen über `apiClient`.
- Rücksprung: `?from=<interner Pfad>` (`utils/profileReturn.ts`). Erlaubt sind nur absolute interne Pfade (kein Schema, kein `//`, kein Backslash, keine Steuerzeichen, auch nicht nach Prozent-Dekodierung); Profil- und Login-Pfade werden abgelehnt (keine Schleifen), serverreservierte OAuth-Parameter und Tour-Parameter entfernt. Die Tabs behalten `from`; «Zurück» und «Abbrechen» führen dorthin, sonst zum aktiven Department bzw. `/dashboard`.
- Zwei Darstellungen derselben Verwaltung über einen gemeinsamen Container (`components/profile/ProfileContainer.vue`, Modus `page` | `modal`, Tabs in `ProfileTabs.vue`, Bereiche = die Views unter `views/profile/`): die geroutete Seite (`ProfileLayout`, `PageShell`) und der Dialog `ProfileModal` (`EDialog`, gehostet in `AppLayout`). Die Views erfahren ihren Modus nur über den injizierten `ProfileContext` (`useProfileContext`: `openTab`, `leave`, `setDirty`); Logik und API sind nicht dupliziert.
- Das Menü «Profil bearbeiten» öffnet das Modal über der aktuellen Seite (URL und Seite bleiben unverändert, Tabs wechseln ohne Neuladen, besuchte Bereiche bleiben per `KeepAlive` erhalten). Läuft die Onboarding-Tour `profile-overview` oder ist man schon auf einer Profilseite, navigiert das Menü stattdessen auf die URL-Ansicht (`/profile?from=<aktuelle Seite>`). «Als Seite öffnen» im Modal führt auf dieselbe URL mit `from`; die URL-Ansicht bleibt der kanonische Einstieg (MFA-Pflicht, OAuth-Rückweg, Direktlinks). Die aktive Department- bzw. GA-Auswahl bleibt unberührt.
- Ungespeicherte Eingaben: Seite → Bestätigung beim Verlassen der Route; Modal → Bestätigung beim Schliessen (Schliessen-Knopf, Escape, Klick daneben) und bei jeder Navigation (Browser-Zurück, Links), über `setDirty` und einen `router.beforeEach` nur solange das Modal offen ist. Reload schliesst das Modal. Das Verknüpfen im Modal parkt die aktuelle Seite als Rücksprung; der Rückweg landet auf `/profile/identities`.
- Layout: Die Seite verwendet `PageShell` in der Standardbreite (wie `/{departmentId}/ga/planung/…`: max. 1400 px, gleiche Seitenabstände) mit Titel, Untertitel und «Zurück» als Aktion; die Tabs (`ProfileTabs`, `v-tabs` mit `materials-view-tabs.css`) stehen im `filters`-Slot unter der Überschrift, der Inhalt scrollt mit der Seite. Das Modal (`EDialog`, `content-class` `profile-modal-dialog`, bis 960 px, oben ausgerichtet) trägt Titelzeile und Tabs im festen Kopf; es scrollt nur der Inhaltsbereich, «Speichern/Abbrechen» bleiben unten sichtbar (sticky). Die Tab-Leiste hat keinen eigenen Scrollbalken und zeigt auf schmalen Displays Pfeile (`show-arrows`).
- Darstellung: `PageShell` für den Seitentitel, `ECard`/`EDialog`, `ETextField`/`ESelect`/`EButton` für Formulare, Farben über die Tokens (`--color-*`, `--v-theme-surface`). Ein Dark-Theme existiert in der App noch nicht (siehe `docs/ui/vuetify-standards.md`). Wird das Profil ohne `from` betreten (Onboarding-Tour, Links aus der App), ergänzt der Router-Guard die vorherige Seite (`profileFromForEntry`); bei frischem Laden oder zwischen Profilseiten wird nichts ergänzt. `AppLayout` verwendet für alle Profilseiten denselben Komponenten-Schlüssel (`layoutViewKey`), damit der Tab-Wechsel die Profilseite nicht neu aufbaut. Ungespeicherte Änderungen auf `/profile` werden beim Verlassen (Tab, Zurück, Navigation) bestätigt.
- Die Adresse wird weiterhin als Department-Adresse (`USER_ADDRESS_TYPE`) gespeichert und braucht ein aktives Department; ohne Department zeigt die Seite einen Hinweis und deaktiviert die Felder.
- Onboarding-Tour `profile-overview`: Schritte 13–18 laufen auf `/profile` (`routeName: 'Profile'`), die `data-onboarding`-Selektoren sind erhalten.
- MFA-Pflicht (`mfa_setup_required`): `main.ts` navigiert auf `/profile/security` (keine Navigation, wenn dort bereits geöffnet).

Department-App hängt unter `/:departmentId/…` (Aktivitäten, Material, Accounting, Werkstatt, Einstellungen). Weitere Flächen: `/admin-dashboard`, `/supplier/:companyId`, öffentliche Seiten (`/`, `/login`, `/i/…` QR), `/display`.

## Authentifizierung

Stateless JWT (Lexik) plus Refresh-Token (`gesdinet/jwt-refresh-token-bundle`).

- Login: `POST /api/auth/login_check` (E-Mail + Passwort), Throttling.
- Refresh: `/api/token/refresh`.
- Sitzungen: Jeder Login (Passwort, Google, MiData) erzeugt genau eine serverseitige `UserSession`; deren UUID steht als Claim `sid` im JWT (`JwtSessionSubscriber`, `JWT_CREATED`). Refresh-Tokens (`refresh_tokens.session_id`) gehören zur Sitzung; ein Refresh (Gesdinet `single_use`) behält die `sid`. Jeder JWT-Request prüft in `JWT_DECODED`, dass die Sitzung existiert, dem User gehört und nicht widerrufen ist (sonst 401); zusätzlich prüft `App\Security\UserChecker` auf Login, Refresh und API den Account-State `active`. Logout widerruft die aktuelle Sitzung, Passwortänderung alle anderen, Passwort-Reset und Deaktivierung alle (jeweils samt Refresh-Tokens, über `UserSessionManager`/`RefreshTokenRevoker`). Ein neuer Login erzeugt eine weitere Sitzung, ohne andere zu widerrufen; MiData-Verknüpfen stellt keine neuen Tokens aus. `last_seen_at` wird höchstens alle 5 Minuten geschrieben.
- Admin-MFA und Step-up: Für globale Security-Admins (`superadmin`, `orgchef`, `suborgchef` — `AdminCapabilityChecker::hasGlobalAdminRole`) setzt `AdminMfaGuardSubscriber` (kernel.request nach der Firewall) zentral durch, was `AdminMfaPolicy` als Adminfunktion bzw. Step-up-Aktion listet (eine Tabelle, keine Prüfungen in Controllern; andere Benutzer und nicht gelistete Routen bleiben unberührt). `AdminMfaGuard` antwortet mit 403 `mfa_setup_required` (kein aktives TOTP), `mfa_required` (TOTP aktiv, aber die Sitzung hat kein `mfa_verified_at`, z. B. vor der TOTP-Aktivierung entstanden oder Legacy-JWT ohne `sid`) oder `step_up_required` (Step-up-Aktion ohne frisches `step_up_at`). `POST /api/auth/step-up` (`StepUpService`) prüft TOTP- oder Recovery Code über den `TotpService` (Replay-Schutz, Sperre, Verbrauch), setzt `UserSession.step_up_at` und — falls noch nicht vorhanden — `mfa_verified_at`; keine neue Sitzung, keine Tokens, nur diese Sitzung. Frische: `StepUpService::FRESHNESS_SECONDS` (600). Step-up-Aktionen: `PATCH /api/users/{id}/admin` mit `global_admin_role`, `admin_capabilities`, `email` oder `state`, `/api/mail/settings` (Schreiben), `/api/admin/integrations/*` (Schreiben), reservierter Pfad `/api/admin/security/*` (Admin-2FA-Reset, noch nicht gebaut). Frontend: der `apiClient`-Interceptor öffnet bei `mfa_required`/`step_up_required` den globalen Step-up-Dialog und wiederholt die Anfrage genau einmal; `mfa_setup_required` führt zu Profil → Sicherheit.
- Sitzungsverwaltung und Trusted Devices (Profil → Sicherheit, `/profile/security`): `GET/DELETE /api/profiles/{id}/security/sessions[/{sid}]`, `POST …/sessions/revoke-others`, `GET/DELETE …/trusted-devices[/{id}]`, `GET …/activity` (`ProfileSecurityController`, nur eigenes Konto). Die aktuelle Sitzung ist nur über Logout beendbar (409 `current_session`); fremde oder unbekannte Sitzungen sind 404. Widerruf läuft über `UserSessionManager` (Sitzung + Refresh-Tokens; das JWT ist über die `sid`-Prüfung sofort 401). Das Beenden anderer Sitzungen (einzeln und «alle anderen») ist über `AdminMfaPolicy::LEVEL_SELF_STEP_UP` step-up-pflichtig, sobald der User TOTP aktiv hat (auch mit Trusted Device); Lesen und Vertrauen widerrufen sind es nicht. Angezeigt werden nur Auth-Methode, aus dem User-Agent abgeleitet Browser/Betriebssystem, Zeiten und MFA-/Trusted-Status; keine IP, kein Fingerprint.
- Trusted Devices (`TrustedDevice`, `TrustedDeviceService`, `TrustedDevicePolicy`): überspringen ausschliesslich die Login-MFA, nie ein Step-up. Erteilt wird das Vertrauen nur im `POST /api/auth/mfa/verify` mit `trust_device: true` nach erfolgreichem TOTP- oder Recovery Code (ein Passwort- oder OAuth-Login allein nie). Credential: 32 zufällige Bytes im HttpOnly-Cookie `emc_td` (Pfad `/api/auth`, SameSite=Lax, damit er auch auf den OAuth-Callbacks ankommt), serverseitig nur sha256, an genau einen User gebunden. Dauer zentral in `TrustedDevicePolicy`: globale Security-Admins 30 Tage, alle anderen 90; geprüft wird gegen die aktuelle Rolle ab Erteilung (nicht gleitend), ein später beförderter User fällt also auf 30 Tage. Login: `MfaChallengeService::issueIfRequired(…, $request)` entfällt die Challenge bei gültigem Gerät; die neue Sitzung wird mit `mfa_source = trusted_device` und `mfa_verified_at` markiert (für den Admin-Guard), `step_up_at` bleibt leer. Widerruf aller Geräte: TOTP deaktivieren/neu einrichten, Passwortänderung, Passwort-Reset, Deaktivierung des Kontos. Sitzung und Trusted Device haben getrennte Lebenszyklen; das Widerrufen eines Geräts beendet keine Sitzung.
- Sicherheitsaktivität: `SecurityActivityService` liefert das persönliche Sicherheitsprotokoll aus `audit_event` (`target_user_id` = eigener User, feste Allowlist von Aktionen: Login, MFA, TOTP, Recovery, Step-up, Trusted Device, Sitzungen, Passwort, E-Mail-Adressen, Profiländerungen, OAuth-Link/-Unlink, Abteilungsrollen). Seitenweise per Cursor (Standard 20, max. 50, `GET …/security/activity?limit&cursor&action&from&to`; `action` nur aus der Allowlist, `from`/`to` als `YYYY-MM-DD` inklusive, sonst 400). Profil-Accordion: 5 sichtbare Zeilen mit internem Scroll und Nachladen; «Gesamtes Protokoll» öffnet `ProfileSecurityLogModal` (40 pro Seite, Filter Typ/Zeitraum). Pro Ereignis nur: Zeit, Typ, Auth-Methode, MFA-Quelle, Browser/OS, IP, handelnder User (bei Fremdaktionen mit Namen), bei Profiländerungen die Feldnamen – nie Feldwerte, Roh-Changes oder Secrets.
- Audit-Kontext: `AuditLogger` speichert bei Sicherheitsaktionen `ip_address`/`user_agent` strukturiert am `AuditEvent` (nur serverseitig via `Request::getClientIp()`), redigiert Change-Felder mit `password|secret|token|hash|…` im Namen und speichert bei `profile_updated` nur Feldnamen. Historische Zeilen ohne Kontext bleiben sichtbar (IP/Browser leer).
- Client-IP und Proxies: `X-Forwarded-For` wird nur von Proxies aus `TRUSTED_PROXIES` (Komma-Liste/CIDR/`private_ranges`) ausgewertet, sonst gilt die Verbindungs-IP; `X-Forwarded-Proto/Host` und `X-Real-IP` werden nicht vertraut. Leer im Repo-Default und lokal; in den Server-Overrides (`deploy/docker-compose.override.*.example.yml`) `172.16.0.0/12` (Docker-Standardpool, später auf das exakte Compose-Netz einzuengen), weil das Backend dort nur über `127.0.0.1` hinter Caddy erreichbar ist.
- Verknüpfte Anmeldungen (Profil → Verknüpfte Anmeldungen, `/profile/identities`): `ExternalIdentity` (`provider` + `external_user_id` global eindeutig; mehrere Identitäten pro User und Anbieter zulässig; `email`/`display_name` nur zur Anzeige, nie für Zuordnung, nie automatisch `UserEmailAlias`). `ExternalIdentityService` verbindet (`attach`, idempotent, fremde Identität → `link_conflict`) und trennt (`unlink` per Identitäts-ID; entfernt nur die Identität, Memberships/Gruppen/Rollen/Struktur-Mappings bleiben). Letzte Anmeldemethode: geschützt, wenn weder Passwort-Weg (aktives Konto + bestätigte Primary-Adresse) noch eine andere Identität übrig bleibt. API: `GET/DELETE /api/profiles/{id}/security/external-identities[/{identityId}]` (nur Verbundenes, keine Platzhalter, nur gekürzte Kennung); Start `POST /api/auth/link/{google|midata}` liefert `authorization_url`.
- OAuth-Einstiegskontext (`AuthIntent`): Der Rückweg eines OAuth-Durchlaufs ist der bereinigte interne Pfad im signierten State (Einladungslink `…/pending-assignment?join_code&invite_id&department_id`, QR/Join-Code `…?join_code`, MiData-Onboarding `…?midata_onboarding|midata_candidate`, geschützte Route = beliebiger interner Pfad, Login ohne Pfad). `AuthIntent::fromRedirect()` leitet daraus serverseitig `login | invitation | join_code | midata_onboarding | protected_route` ab, `link_identity` setzt nur der explizite Link-Start; der Intent steckt im State-Cookie (Google und MiData), kommt nie vom Client und gilt genau einen Callback (State einmalig). Rückwege sind nur interne Pfade (`AuthIntent::sanitizeRedirect`), die server-reservierten Parameter `profile_security|oauth|provider|reason` werden aus nutzergelieferten Pfaden entfernt. Einladung/Join-Code/Onboarding werden nach dem Login unverändert vom bestehenden Prozess in `PendingAssignmentView` bzw. MiData-Callback fortgesetzt (erneute serverseitige Validierung, keine automatische Annahme); ein Abbruch oder Fehler kehrt mit `redirect=<ursprünglicher Pfad>` zum Login zurück. Nur `link_identity` führt nach Profil → Sicherheit.
- Link-Ergebnis: Das Ergebnis (Erfolg/Fehlergrund) liegt serverseitig (`LinkResultStore`, 5 min, einmalig, an die Sitzung gebunden); die Rückkehr-URL trägt nur `?profile_security=1`. Der Link-Start parkt den Rücksprungpfad (`from`) im `sessionStorage`, weil der Rückweg die Query verwirft. `/profile/identities` fragt `GET /api/profiles/{id}/security/external-identities/link-result` genau einmal ab, meldet das Ergebnis und entfernt die Hinweis-Parameter (präparierte URLs, Neuladen und normaler Login zeigen nichts). Trägt ein älterer Link den Hinweis auf einer anderen Seite, leitet der Router-Guard nach `/profile/identities` weiter. Router-Redirects (`/dashboard`, `/`, Pending-Seite verlassen) nehmen den Hinweis über `carryOAuthReturnParams` mit.
- OAuth-Link-Flow: Start per POST (Step-up/Reauth greift vor dem Controller). State-Cookie (signiert, 10 min, HttpOnly) trägt User-ID, Sitzungs-ID, PKCE-Verifier und OIDC-Nonce; Google prüft die Nonce im `id_token` des Token-Endpoints, MiData wie bisher. Die OAuth-Firewalls laufen mit `security: false` (Login hat noch keinen User); der Link-Callback prüft das BEARER-Cookie deshalb explizit über `OAuthCallbackSessionResolver` (Signatur, Ablauf, `sid`, nicht widerrufen, aktives Konto). Der Callback verlangt denselben eingeloggten User **und** dieselbe Sitzung (`session_mismatch` sonst); ein abgelaufenes/fehlendes JWT führt zu `/login?oauth=error&reason=session_expired` statt zu einem 401 und ordnet nie etwas zu. Ein Abbruch beim Anbieter kehrt im Link-Flow ins Profil zurück (`reason=denied`), der State ist einmalig (`OAuthStateReplayGuard`, Cache) und Redirects sind nur interne Pfade. Verbinden ist kein Login: kein neuer User, keine Tokens, bei MiData kein Onboarding/Join/Gruppenimport. Rückweg: `?profile_security=1&oauth=linked|error&provider=…&reason=…` öffnet Profil → Sicherheit (TopHeader) ohne Profil-Reload. Der Browser-Start `GET /api/auth/link/midata` (Onboarding, Gruppenimport) prüft dieselbe Policy nur beim erstmaligen Verbinden von MiData und kehrt bei Ablehnung mit `reason` zurück (TopHeader zeigt den Hinweis); wer MiData schon verbunden hat, bestätigt dort nur dieses Konto: ein weiteres Konto lehnt `MiDataOAuthAccountService` mit `additional_account` ab (nur über Profil → Sicherheit).
- Step-up/Reauth (`AdminMfaPolicy::LEVEL_SELF_SENSITIVE`, nur Verbinden/Trennen): User mit TOTP brauchen frisches Step-up (globaler Dialog), globale Admins wie `LEVEL_STEP_UP`, User ohne TOTP eine Anmeldung dieser Sitzung innerhalb von `AdminMfaGuard::RECENT_LOGIN_SECONDS` (600 s; Legacy-Sitzungen zählen nie), sonst `reauth_required` (Hinweis: neu anmelden). Kein TOTP-Code in OAuth-Controllern.
- Department-E-Mail-Zuordnung: `Membership.notificationEmail` bleibt der einzige Speicher. Lesen aller eigenen Mitgliedschaften `GET /api/profiles/{id}/emails/department-assignments`, Ändern über das bestehende `PUT /api/departments/{id}/my-notification-email` (nur eigene Membership, nur eigene verifizierte Adressen, Rückfall auf die Hauptadresse; Audit `membership_notification_email_changed`, im Sicherheitsprotokoll sichtbar). Die Anzeigen in Sicherheit und Department-Einstellungen gleichen sich über das Browser-Event `emc-profile-emails-changed` (`detail.source`) ab. Hat nichts mit der OAuth-Anmeldung zu tun.
- Audit-Indizes: `audit_event` ist die einzige, zentrale Tabelle (keine Tabelle pro User). Die Protokollabfrage (`target_user_id` = User, `created_at DESC, id DESC`, Cursor auf `(created_at, id)`) nutzt `idx_audit_target (target_user_id, created_at)` per Backward-Scan, `id` sortiert nur Gleichstände inkrementell nach; der Akteur-Index `idx_audit_actor` besteht bereits. Es wurde bewusst kein weiterer Index ergänzt.
- Audit-Aufbewahrung (Ist): Es gibt keine zeitbasierte Löschung. Zeilen werden nur durch `DepartmentResetService` entfernt (`DELETE … WHERE department_id`, explizites Department-Reset). Fachliche Audit-Ereignisse zu Material, Departments und Grossanlass bleiben unabhängig von den 90 Tagen erhalten.
- E-Mail-Modell (nicht vermischen): `Profile.email` = globale Hauptadresse (oberes Profilfeld, schreibgeschützt; Stift springt zu Sicherheit → E-Mail-Adressen), `UserEmailAlias` = zusätzliche verifizierte Login-Adressen (`/api/profiles/{id}/emails`), `Membership.notificationEmail` = Benachrichtigungsadresse je Department/GA (`MembershipNotificationEmailResolver`, Rückfall auf die Hauptadresse). Änderungen in Sicherheit lösen `emc-profile-emails-changed` aus; die Department-Auswahl lädt neu.
- Aufbewahrung Kontext: `SecurityActivityService::CONTEXT_RETENTION_DAYS` (90). `php bin/console app:security-activity:purge-context` leert danach IP und User-Agent der Sicherheitsereignisse; die Audit-Zeilen selbst werden nicht gelöscht (es gibt keine globale Audit-Aufbewahrung). Einplanung: Host-Cron wie bei der Medien-Retention (siehe `deploy/SERVER-UPDATE.md`, «Cron: Sicherheitsprotokoll»); es gibt keinen internen Scheduler. Verknüpfte Anmeldungen: Google nur Statusanzeige (kein Link-/Unlink-Flow, offen); MiData trennen entfernt nur die `ExternalIdentity`, Memberships/Gruppen bleiben; keine Account-Zusammenführung über E-Mail.
- Organisations-Scope globaler Admins: Ein Scope nur aus Department-Wurzeln (`organisation_ids = []`) ergibt Zugriff auf die Organisationen dieser Wurzeln (`AdminCapabilityDepartmentScope::organisationIdsForDepartments`), nicht auf alle; unbekannte Wurzeln ergeben keinen Zugriff. Ein komplett leerer Scope bleibt bewusst unbeschränkt.
- Übergang (befristet, `LegacySessionCutoff`): JWTs ohne `sid` werden nur akzeptiert, wenn sie vor der Ausführung der Migration `Version20261005120000` ausgestellt wurden; Refresh-Tokens ohne Sitzung nur, wenn sie davor erstellt wurden — sie erhalten beim Refresh eine Sitzung mit `auth_method = legacy`. Nach Ablauf der Refresh-TTL (30 Tage) entfernen und `session_id` auf `NOT NULL` setzen.
- Öffentlich ohne JWT: Registrierung, Verify, Passwort-Reset und OAuth-Login/-Callback unter `/api/auth/`, `/api/public`, `/api/health` und `/api/token/refresh`. MiData-Verknüpfung (`/api/auth/link/midata`) erfordert einen eingeloggten User.
- Übrige `/api`- und `/media`-Routen: `ROLE_USER`.
- Google, MiData und Microsoft haben eigene Firewalls (`/api/auth/google`, `/api/auth/midata`, `/api/auth/microsoft`). MiData verwendet OIDC-Discovery und speichert nur `(provider, sub)` als ExternalIdentity; Provider-Tokens bleiben transient. Der normale MiData-Login (`/api/auth/midata`) sendet `prompt=login`: Hitobito meldet eine bestehende MiData-Browser-Session ab und verlangt eine erneute Anmeldung, damit keine fremde Session unbemerkt übernommen wird. Link- und Onboarding-Flow (`/api/auth/link/midata`) senden kein `prompt`, weil der Callback dort die MiData-Person gegen die verknüpfte Identität prüft. Ein eMatChef-Logout beendet die MiData-Session nicht; ein Remote-Logout über den `end_session_endpoint` ist bewusst nicht umgesetzt (er bräuchte ein gespeichertes ID-Token).
- Die MiData-OAuth-Anforderung umfasst `openid email with_roles groups people`. Die `/oauth/userinfo`-Antwort wird im Callback zu einem typisierten DTO normalisiert. `with_roles` liefert unter anderem `primary_group_id` und Rollen mit `group_id`, `group_name`, `role`, `role_class`, `role_name` und `permissions`; sie enthält keine verlässlichen `start_on`/`end_on`-Aktivitätsdaten. Der kurzlebige OAuth-Access-Token bleibt im Callback-Speicher und wird nicht persistiert.
- `HitobitoApiClient` verwendet Symfony HttpClient und provider-keyed Issuer-Konfiguration. `GET /api/groups/{id}` und `GET /api/roles?filter[person_id]=…` werden als JSON:API gelesen; Gruppen-Parent- und Layer-IDs werden aus expliziten Attribut-IDs oder, falls diese fehlen, aus Relationship-`data.id` gelesen. Eine vorhandene Relationship ohne `data`-Key (z. B. nur mit `meta`) liefert keine zusätzliche ID und widerspricht einer vorhandenen Attribut-ID nicht. Rollenlisten folgen sicheren same-origin-Paginierungslinks. Die Rollen-JSON:API liefert detailliertere Role-Ressourcen inklusive `start_on`/`end_on` und wird für zeitbezogene Prüfungen wie Phase-5-Join-Verifikation verwendet, nicht zusätzlich für die primäre Rollen-Erkennung beim normalen Onboarding. Die Parent-Chain-Prüfung vergleicht nur externe IDs, stoppt nach höchstens 64 Ebenen und bestätigt bei Lücken, Zyklen oder unbekannten Gruppen keine Zugehörigkeit. API-/Berechtigungsfehler bleiben explizite Fehler.
- `PbsGroupTypeClassifier` klassifiziert bekannte PBS-Gruppentypen nur als ignoriert (Root), Organisations- (Bund), Department- (Kantonalverband, Region, Abteilung) oder Group-Kandidaten (Stufen). Er erzeugt keine eMatChef-Strukturen und ändert keine Mitgliedschaften oder Rollen. Der Login zeigt CeviDB und JublaDB als „demnächst“; für sie sind keine OAuth-Flows eingerichtet.
- Ein Department-Join-Code identifiziert nur das Department. Beim MiData-OAuth-Callback wird ein aus dem HMAC-signierten OAuth-State wiederhergestellter Join-Code serverseitig erneut aufgelöst und mit dem kurzlebigen Access-Token geprüft: Aktive MiData-Rollen müssen exakt der gemappten MiData-Abteilung entsprechen oder nachweisbar darunter liegen. Bei Bestätigung wird eine fehlende Membership mit Rolle `u` erstellt; vorhandene Membership-Rollen bleiben unverändert. Ein vorhandener offener JoinRequest wird ohne erfundenen menschlichen Reviewer abgeschlossen. Die Phase-5-Prüfung gibt ihre aktive, auf diese Abteilung begrenzte Rollenliste an `MiDataGroupMembershipSynchronizer` weiter. Dieser legt GroupMemberships additiv und ausschließlich für bereits auf bestehende eMatChef Groups gemappte direkte externe Gruppenrollen desselben Departments an. Unmapped-Gruppen werden protokolliert; Cross-Department-Mappings werden als Konflikt protokolliert und nicht übernommen. Bestehende GroupMembership-Eigenschaften bleiben unverändert; Standardzuordnungen erhalten nur `member`, `canProcure=false` und `isPrimary=false`. Es gibt keine Ancestor-Zuordnung, keine Löschung, keinen Strukturimport und kein automatisches Department-Rollenmapping. Ohne MiData-Identität oder Department-Mapping sowie bei erfolgreich geprüften Rollen ohne Treffer legt der Callback keine manuelle Anfrage an; diese wird erst durch die erneute Formularübermittlung mit der bestehenden Turnstile-Prüfung erstellt. Technische Verifikationsfehler erzeugen weder Membership noch JoinRequest und liefern eine generische temporäre Fehlerantwort mit MiData-Wiederholungsmöglichkeit. OAuth-Tokens bleiben transient und werden weder gespeichert noch an das Frontend gegeben.
- MiData-Onboarding für Materialwart und Abteilungsleitung (nur PBS): PBS-Strukturmodell: `Group::Root` wird ignoriert und nie einem eMatChef-Objekt zugeordnet; `Group::Bund` entspricht einer eMatChef-`Organisation`; `Group::Kantonalverband`, `Group::Region` und `Group::Abteilung` entsprechen Departments (Kantonalverband ohne Parent, Regionen darunter, Abteilung unter der letzten Region bzw. direkt unter dem Kantonalverband); PBS-Untergruppen sind Groups und nicht Teil dieses Flows. Die Bund-Zuordnung wird ausschliesslich administrativ über `app:external-structure:map` hergestellt; das Onboarding erzeugt die Bund-Organisation nie. Meldet sich ein MiData-User ohne eMatChef-Membership an, nominieren die userinfo-Rollen nur Kandidaten. `MiDataMaterialwartVerifier` bestätigt über `GET /api/roles` eine aktive direkte unterstützte Rolle (`start_on`/`end_on` inklusive) exakt in der Gruppe. Unterstützt sind nur die technischen Rollenklassen im `MiDataSupportedRoleCatalog`: `Group::Abteilung::Materialwart` → `mw` (Priorität 0) und `Group::Abteilung::Abteilungsleitung` → `dc` (Priorität 1); `Group::Abteilung::AbteilungsleitungStv` und alle anderen Rollen werden ignoriert. Hat ein User in einer Abteilung mehrere unterstützte Rollen, gilt die mit der höchsten Priorität; die frische Prüfung bestimmt die Membership-Rolle, eine gespeicherte Rollenklasse ist nur Absicht. Der Verifier und verlangt die Kette Abteilung → Region* → Kantonalverband → Bund (→ Root). Rollen- und Gruppennamen sowie Browserdaten sind nie Autorisierungsmerkmale. Ein `MiDataDepartmentOnboarding`-Angebot (User, Provider, externe Person, externe Abteilung, Rollenklasse, Anzeigenamen, Ablauf nach 24 h; keine Tokens) entsteht nur, wenn der Bund bereits auf eine Organisation gemappt ist; im Callback wird keine Struktur angelegt. `/pending-assignment` zeigt es über `GET /api/join-requests/midata-onboarding`. „Abteilung einrichten“ startet den MiData-Link-Flow mit der Angebots-ID im HMAC-signierten State; erst dieser Callback prüft mit frischem Token Angebotsbesitz, Ablauf, verknüpfte Identität, aktive Rolle, Struktur und Bund-Mapping erneut. Verknüpft wird ausschliesslich über `ExternalStructureIdentity(provider, external_group_id)`; bestehende Mappings werden nur bei passendem Zieltyp, passender Organisation und passendem Parent wiederverwendet, sonst Konflikt ohne Reparatur oder Verschiebung. Namen verknüpfen nie; ein gleicher oder sehr ähnlicher Name unter demselben erwarteten Parent (bzw. auf Root-Ebene derselben Organisation) stoppt als Konflikt, unter anderen Parents nicht. Die Anlage (Departments, Mappings, Membership `mw` bzw. `dc`) läuft in einer Doctrine-Transaktion unter einem PostgreSQL-Advisory-Lock pro Kantonalverband; der Unique-Index auf `(provider, external_group_id)` bleibt Rückfallschutz. Eine bestehende Membership wird nie verändert. Mehrere Zugehörigkeiten: Pro MiData-Abteilung entsteht höchstens ein Angebot, auch wenn der User schon Memberships hat (Abteilungen, in deren gemapptem Department er bereits Mitglied ist, entfallen). Kandidaten werden pro Abteilung dedupliziert (mw gewinnt) und nach Rolle (mw vor dc) und Name sortiert. Bis zu 10 relevante Abteilungen werden beim Login vollständig geprüft; `/api/roles` wird dafür einmal geladen und `HitobitoApiClient` lädt jede Gruppe pro Request höchstens einmal. Bei mehr als 10 gilt der Suchmodus; höchstens 10 mw-Abteilungen werden trotzdem direkt geprüft und angeboten, dc-Abteilungen nur über die Suche. Dafür speichert der Callback ungeprüfte Kandidaten (`MiDataMembershipCandidate`: User, Provider, externe Gruppe, Rollenklasse, Anzeigename, Ablauf; keine Tokens oder Hierarchie) und `/pending-assignment` bzw. das Profil zeigen eine Suche nur über diese eigenen Kandidaten (`GET /api/join-requests/midata-onboarding/candidates`). Ein Suchtreffer autorisiert nichts: Die Auswahl startet den Link-Flow mit der Kandidaten-ID im signierten State; erst dieser Callback prüft mit frischem Token vollständig, legt das Angebot an und richtet es ein. Ungeprüfte Kandidaten zählen nicht als verifizierte Alternative für die Support-Queue. Weitere Memberships sind nicht primär; offene Angebote bleiben nach einer Einrichtung bestehen und sind für User mit Membership im Profil unter „Weitere MiData-Zugehörigkeiten“ erreichbar. Ein offenes Angebot ersetzt den generischen Prozess „Benutzer ohne Zuordnung“ (`MiDataOnboardingQueueExclusion`); nach erfolgreicher Einrichtung wird eine noch offene System-Anfrage des Users ohne Reviewer auf `assigned` mit dem eingerichteten Department gesetzt (Event `assigned`, Quelle `midata_onboarding`).
- Passwort-Hashing: Symfony `auto` auf `User`.

Department-Rechte kommen nicht aus dem JWT allein, sondern aus `Membership.role` im angefragten Department. Katalog: `DepartmentRole`, Zuweisungslogik `MembershipRoleCatalog`.

Support-Anfragen (`AdminJoinRequest`): Department-Manager (`mw`/`dc` ohne globale Admin-Rolle) sehen offene Anfragen und Verlauf, lehnen ab und weisen zu (Zuweisung nur `mw`) ausschliesslich für Anfragen ihrer Organisation, deren gewünschtes Parent-Department ihr Department oder ein Unter-Department ist (`AdminJoinRequestManagerScope`). Anfragen ohne Organisation oder ohne Parent-Department bleiben globalen Admins vorbehalten. Zuweisungen durch Manager müssen im eigenen Teilbaum liegen und `MembershipRoleCatalog::isAllowed`/`canAssign` erfüllen; der Fallback „Ziel ohne mw/dc → zugewiesener User wird mw“ gilt nur für globale Admins. Org-/Sub-Org-Admins lehnen nur Anfragen ihrer zugänglichen Organisationen oder ohne Organisation ab; Superadmins bleiben global.

Die Support-Liste `GET /api/join-requests/admin-request/pending` ist rein lesend. Globale Admins sehen dort zusätzlich berechnete Einträge „Benutzer ohne Zuordnung“ (`request_kind: unassigned_user`, ohne Anfrage-ID; `UnassignedUserSupportQueue`): aktive User ohne Membership, ohne offene JoinRequest, ohne eigene offene AdminJoinRequest, ohne verifizierte Alternative und ohne ausgeblendete System-Anfrage; Superadmin-, E2E-Smoke- und reine Lieferantenkonten sind ausgenommen. Gespeichert wird erst bei einer expliziten Admin-Aktion (`POST /api/join-requests/unassigned-users/{userId}/assign` bzw. `/dismiss`) als AdminJoinRequest mit `assigned` bzw. `rejected`; eine abgelehnte System-Anfrage blendet den User dauerhaft aus. System-Anfragen (Altbestand `auto_created`, Queue-Aktion `queue_created`) werden über ihre Events erkannt, nicht über den Text. Verifizierte Alternativen (z. B. ein offenes MiData-Angebot) melden sich über `UnassignedUserQueueExclusion`; solange sie bestehen, erscheinen offene System-Anfragen des Users weder in der Support-Liste noch in `/mine`. Eigene Anfragen bleiben bei der Registrierung bzw. auf `/pending-assignment` explizite Aktionen des Users.
